**Figure 820: Retried Command Affects Another Host**

The diagram illustrates a scenario involving two hosts (Host 1 and Host 2) and three controllers (Controller 1, Controller 2, Controller 3). The timeline shows:

- **Host 1** sends a "Write A at Location X" command to **Controller 1**.
- **Controller 1** begins processing the command (indicated by a blue square).
- **Host 1** detects a loss of communication with Controller 1.
- Host 1 determines that Controller 1 has stopped processing the command.
- Host 1 retries the command: "Write A at Location X" to **Controller 2**.
- **Controller 2** processes the retry and returns "Success".
- Meanwhile, **Host 2** sends a "Read Location X, observe A" command to **Controller 3**, which returns "Success".
- Host 2 then sends a "Write B at Location X" command to Controller 3, which also returns "Success".
- The diagram concludes with a red text note: "**Location X is A not B!**", indicating an inconsistency.

A legend indicates that the blue squares represent "Controller processing command".

This sort of higher-level software usage of ordinary NVMe commands (e.g., NVM Command Set Write commands) for coordination and synchronization among multiple hosts is strongly discouraged because retry of these commands after communication loss is problematic. Higher-level software should instead use mechanisms intended for coordination among multiple hosts. Two examples of such mechanisms are:

- Reservations (refer to section 8.1.24); and
- Compare and Write fused operations (refer to the Fused Operation section of the NVM Express NVM Command Set Specification).

In addition, command retries that modify NVM subsystem state (e.g., a Set Features command that modifies a feature that has any scope that is visible to other hosts as described in Figure 403) are able to affect the behavior of other hosts. Use of commands that modify NVM subsystem state for coordination and synchronization among multiple hosts is likewise strongly discouraged.
